# 力量体系（power system）设计 + 逐章一致性自检

> 穿越/系统流/修仙/玄幻爽文的命门：**等级、成长值、战力数值跨章严丝合缝且合理**。读者最恨等级跳变、
> 战力前后矛盾、属性突变无理由、升级节奏崩（数值膨胀/越级无代价）。本文是力量体系的人读设计指南 +
> 机检判据总纲。机器真值在 `novel/_lib/power_system_defs.py`（题材/母题关键词、等级模板、面板默认、节奏默认、
> 单调字段）+ `设定/power_system_registry.json`（本剧定义 + 逐章成长 progression）。引擎在
> `novel-wiki/scripts/power_system.py`，写章后自检由 `novel/scripts/post_write.py` + `novel-review` 跑。

## 1. 为什么要机检（战力崩坏的根因）

网文公认规律：**读者爽感 ∝ log(战力数据)**——线性涨战力，爽感增量递减；于是作者倾向指数膨胀战力来续爽，
长篇必然"战力崩坏"（后期数字失去意义、前后打架）。光靠人脑记不住几百章的等级/属性，所以要把力量体系
**结构化 + 逐章机检**：等级/境界/战力只增不减、跨章排序一致、升级有节奏有代价。这正是 n2d 那套
"系统面板母题成长状态机（只进不退）"在小说文本侧的对应。

## 2. 力量体系登记（设定/power_system_registry.json）

立项时 novel-create 按题材脚手架一份骨架（`power_system_defs.starter_registry`），作者按设定圣经覆盖：

```jsonc
{
  "kind": "novel_power_system_registry",
  "version": 1,
  "system_type": "系统流",            // 系统流|修仙|玄幻|通用（detect_system_type 按题材给默认）
  "tiers": {                          // 等级体系（有序·单一真值源）
    "kind": "level",                  // level=数值等级 / realm=命名境界
    "sequence": [],                   // realm 时填境界序列（修仙默认见下）
    "subtiers": [],                   // 修仙每境界分 初/中/后/大圆满
    "level_cap": 100                  // level 时填等级天花板（开篇先定！见 §4）
  },
  "panel_schema": {                   // 系统流面板字段（属性 ≤ 7）
    "level_field": "等级", "exp_field": "经验值",
    "attrs": ["力量", "敏捷", "体质", "精神", "幸运"],
    "resources": ["技能点", "积分"]
  },
  "pacing": { ... },                  // 升级节奏目标（默认见 §4）
  "progression": [                    // 逐章成长快照（单调·机检不回退）
    {"chapter": 1, "character": "主角", "level": 1, "tier": "练气初期",
     "attrs": {"力量": 10, "敏捷": 8}, "战力": 10},
    {"chapter": 5, "character": "主角", "level": 5, "tier": "练气后期",
     "attrs": {"力量": 30, "敏捷": 22}, "战力": 45}
  ]
}
```

## 3. 等级体系模板（研究落地·候选默认，采集 2026-06-19）

- **修仙标准境界（凡人修仙传体系）**：练气 → 筑基 → 结丹 → 元婴 → 化神 → 炼虚 → 合体 → 大乘 → 渡劫
  （上界续：真仙/金仙/太乙/大罗）；每境界分 **初期/中期/后期/大圆满**。同境界内的"积累/沉淀"深度
  影响突破后战力——所以同境界层数也算成长档，机检也看它单调。
- **玄幻斗气类候选**：斗者→斗师→大斗师→斗灵→斗王→斗皇→斗宗→斗尊→斗圣→斗帝。
- **系统流**：数值等级 Lv.1→cap，无命名境界；**开篇必须先定等级天花板**（见 §4）。
- 这些只是"未声明时的合理默认"，作者用设定圣经 `## 力量 / 金手指体系` 覆盖即生效，机检按本剧 registry 的 `tiers.sequence` 校验，不强加默认序列。

## 4. 系统面板 + 升级节奏（研究落地）

**面板设计（系统流）**：
- **属性 ≤ 7**：5 核心（力量/敏捷/体质/精神/幸运）+ 至多 2 特殊（因果值/气运/悟性…）。超 7 个=信息过载，删。
- **每个属性 ≥ 每 10 章要在剧情里起一次作用**，否则是装饰位（机检 `attr_relevance_window`，建议级提醒）。
- 面板字段：等级 / 经验值 / 属性 / 技能点 / 积分（商城点）。

**升级节奏（奖励节拍·防数值膨胀）**：
- **每章**：小奖（经验值 / 常见道具 / 线索，量级如 经验+50）。
- **每 5 章**：中奖（属性突破 / 新技能）。
- **每 20 章**：大奖（隐藏任务 / 稀有装备 / 越阶 rank jump）。
- **开篇先定数值天花板**：总等级上限、每档间隔（如每 10 级一个大台阶）、每级属性增量——在 registry 写死，
  后续章按它推进，避免边写边膨胀。
- **越级有界**：单章境界/大级跳变默认 ≤ 1（`max_tier_jump_per_chapter`）；越级必须配明确代价/机缘（吃药、
  奇遇、透支），否则机检疑似数值膨胀（建议级）。

## 5. 机检判据（power_system.py 引擎 → novel-review / post_write）

逐章扫 progression + 正文，findings 用 novel-review 标准形 `{type, entity, severity, chapter, evidence, note}`：

| 检查 | 判据 | 严重度 |
|---|---|---|
| 等级/境界/战力**退档** | progression 同角色某章 < 之前章（且无 `regress_reason` 跌境/废修/封印豁免） | **阻断级** |
| **未知境界** | progression 的 `tier` 不在 `tiers.sequence`（含 subtier）里 | **阻断级** |
| **战力排序矛盾** | 同章 A>B 但他章无事件却 B>A（跨章战力颠倒） | **阻断级** |
| 属性**超 7** / 不在 panel_schema | 面板属性数 > 7 或出现未声明属性 | 建议级 |
| **越级过快** | 单章 tier/level 跳变 > `max_tier_jump_per_chapter` 且正文无代价/机缘词 | 建议级 |
| **属性装饰位** | 某属性连续 > `attr_relevance_window` 章未在剧情起作用 | 建议级 |
| **母题桥段缺席** | 系统流但连续多章无系统面板/升级桥段（读者要的爽点节拍断了） | 建议级 |
| **节奏偏离** | 大奖/中奖间隔明显偏离 pacing 目标 | 建议级 |

阻断级 = 硬矛盾必须改；建议级 = 节奏/设计提醒，不挡流程。`力量体系自检=仅建议` 时全部降为建议级；
`关闭` 时不跑。

## 6. 实时自检接线（写小说过程中持续保证合理）

- **写章前**：`context_loader` 把 `power_system_registry.json`（当前等级/属性/战力）喂给写章上下文，
  让作者/AI 在已知"主角现在 Lv.5、力量 30"的前提下写，而不是凭空发明。
- **写章后**：`post_write.py` 每章跑 `power_system.py` 自检（题材属 `POWER_GENRES` 且 `力量体系自检≠关闭` 时），
  把本章新等级/属性/战力对账 registry，发现退档/矛盾即报，并把本章快照累积进 progression。
- **审稿**：`novel-review` 的 `consistency_audit.py` 把 power_system 作为一个子 runner，与 logic_sentry
  （死人复活/数值漂移）、mechanical_check、style 并列，出审稿报告。

加新题材/新体系只需在 `power_system_defs.py` 加题材关键词 + 等级模板候选，引擎按 registry 泛化，不改判据代码。
